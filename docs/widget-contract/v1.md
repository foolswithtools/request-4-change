# Widget contract v1

Version `1.0.0`. This is what a host app builds against to embed the request-4-change widget. A breaking change bumps the major version and gets a new document; additions that existing hosts can ignore bump the minor version.

```js
customElements.get('r4c-widget').contractVersion // "1.0.0"
```

## Path prefix

Everything request-4-change serves on the host's domain lives under one path prefix, `/__r4c/` by default. The installation can change it (`R4C_PREFIX`). The host app must not serve anything under that prefix: the load balancer routes it to the `edge` sidecar.

| Path | What |
|---|---|
| `GET <prefix>widget.js` | The widget, one ES module. `Content-Type: text/javascript`, `Cache-Control: public, max-age=300`. No credentials needed. |
| `POST <prefix>api/requests` | Submit a request (below). |
| `GET <prefix>api/requests/<requestId>` | Read a request's stage, with the same `Authorization` header as the submit. |
| `GET <prefix>healthz` | Edge's health check. |

The widget learns the prefix from its own script URL: it posts to the directory it was loaded from (`new URL('.', import.meta.url).pathname`), on the page's origin. A host that changes the prefix changes only the `src` of the script tag. Load `widget.js` from the host's own origin, through the prefix, never from a CDN or another domain: only the path of the script URL is used.

## Embed

```html
<script type="module" src="/__r4c/widget.js"></script>
<r4c-widget app-id="my-app" token-url="/session/r4c-token"></r4c-widget>
```

| Attribute | Required | Meaning |
|---|---|---|
| `app-id` | No | The host app's id, as registered in `control` (`host-app add`). The widget does not read it in v1: the app is identified by edge's `R4C_APP_ID` and the assertion's `app_id` claim. No 1.x version will make it required. |
| `token-url` | One of the two | A **same-origin** path. Before each submit, the widget resolves it against the page URL, refuses it if the result is on another origin, and sends `GET` to exactly that URL with `credentials: 'same-origin'`, `cache: 'no-store'` and `redirect: 'error'` (a redirect fails the token instead of being followed). It reads `{"token":"<jwt>"}` from the JSON answer. |
| `token` | One of the two | The assertion itself, injected by the host. The host keeps it fresh (it expires within 5 minutes); the widget reads the attribute at each submit. |

If both are set, `token-url` wins.

## Requester assertion

The token is a JWT the host signs, with RS256 or ES256 and a `kid`, using a key published in its JWKS over HTTPS (see [Security model](../security-model.md#requester-identity)). Claims: `sub`, `email`, `roles`, `app_id`, and `exp` at most 5 minutes ahead. The widget sends it only as `Authorization: Bearer <jwt>`, never in a URL, and takes a fresh one for every submit.

## Form

The form has three labelled fields, operable by keyboard alone:

| Field | Control | Rule |
|---|---|---|
| Kind | select: Bug, Feature, Not sure | `bug`, `feature` or `unsure` (default) |
| Title | text input | 3 to 200 characters |
| Description | textarea | 1 to 20,000 characters |

The browser's own validation stops a submit that breaks a rule. `pageUrl` is the page's origin and path (`location.origin + location.pathname`), when that is an `http(s)` URL of at most 2,048 characters. The query string and fragment are never sent: they can carry sign-in or magic-link tokens. Identity fields such as an email are never part of the form: identity comes only from the assertion.

## Submit

```http
POST /__r4c/api/requests
Authorization: Bearer <jwt>
Content-Type: application/json
Idempotency-Key: <uuid>
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01

{"kind":"bug","title":"Export does nothing","description":"…","pageUrl":"https://app.example.com/reports"}
```

- **`Idempotency-Key`:** a random UUID per submission. Retries of that submission reuse it, and so does pressing Send again on the unchanged form after a failure. Editing the form, or a success, starts a new one. Control answers a repeated key with the first `requestId`, so a retry never creates a second request.
- **`traceparent`:** a new W3C trace context per submission, sampled. Edge continues it, so the host's trace backend can follow the request through edge and control.
- **Retries:** the widget retries when no answer arrives (a dropped connection) or on 502, 503 or 504, up to two more times, after 0.5 s and 1.5 s. It does not retry any other status, including 429 and 500.
- **Cookies:** the submit carries none (`credentials: 'omit'`); only the token-url call sends the host's cookies, to the host's own path.

## Events

Both events bubble and cross the shadow boundary (`bubbles: true, composed: true`), so a listener on `document` hears them.

| Event | `detail` | When |
|---|---|---|
| `r4c-submitted` | `{ requestId }`, a UUID | The request was created, or a retry returned the existing one. The form is cleared. |
| `r4c-error` | `{ error, retryAfter? }` | The submission failed. The form keeps its text. |

`error` is one of:

| Code | Cause |
|---|---|
| `invalid_assertion` | 401: the token was refused. |
| `invalid_body` | 400: the fields broke a rule. |
| `not_found` | 404 with that code. |
| `too_large` | 413: the body is over 32 KB. |
| `rate_limited` | 429. `retryAfter` is `Retry-After` in seconds, when present. |
| `unavailable` | No answer, or 502, 503 or 504, after the retries. |
| `server_error` | Any other failure without one of the codes above, such as a 500 with an empty body. |
| `token_unavailable` | Neither `token` nor `token-url` gave a token, `token-url` failed, or it is not same-origin. Nothing was posted. |

The first five are the intake API's error codes; the last three are the widget's own.

## Styling

The widget renders in an **open shadow root**, so the host's CSS does not reach inside it. The host styles it only through six CSS custom properties, set on `r4c-widget` or any ancestor:

| Token | Used for | When unset |
|---|---|---|
| `--r4c-font-family` | All text | Inherited from the host |
| `--r4c-color-fg` | Text and borders | Inherited from the host |
| `--r4c-color-bg` | Background, and the button's label | Transparent (button label: the system `Canvas` color) |
| `--r4c-color-accent` | The button and the focus ring | The inherited text color |
| `--r4c-radius` | Corners of fields and the button | `4px` |
| `--r4c-spacing` | Gaps and padding | `0.75em` |

Theming beyond these six and localisation are not part of v1.

## Host example

On `https://app.example.com`, with request-4-change's edge sidecar behind `/__r4c/` and the host's session endpoint at `/session/r4c-token`:

```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8">
    <title>Reports · Example App</title>
    <script type="module" src="/__r4c/widget.js"></script>
    <style>
      r4c-widget {
        --r4c-font-family: system-ui, sans-serif;
        --r4c-color-accent: #0b5fff;
        --r4c-radius: 8px;
        max-width: 32rem;
      }
    </style>
  </head>
  <body>
    <h1>Reports</h1>
    <r4c-widget app-id="example-app" token-url="/session/r4c-token"></r4c-widget>
    <script>
      document.addEventListener('r4c-submitted', (e) => console.log('request', e.detail.requestId));
      document.addEventListener('r4c-error', (e) => console.warn('request failed', e.detail.error));
    </script>
  </body>
</html>
```

The session endpoint, on the host's own server, answers the signed-in user with:

```json
{"token":"<JWT signed with the host's key: sub, email, roles, app_id \"example-app\", exp within 5 minutes>"}
```
